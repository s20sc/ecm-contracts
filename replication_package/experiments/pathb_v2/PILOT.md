# Quarantined pilot (PROTOCOL.md Section 14)

Purpose: run six C1/C2 cases through the whole v2.1 pipeline before the freeze, to measure yield, time, and failure modes, and to catch protocol defects. Pilot cases are reported as pilot, never as results.

| case | why chosen |
|---|---|
| robust_248cb38 | primary-source classification test (V18 called it a frame mismatch; the fix is quaternion component order) |
| robust_263650d | UPGRADE with a provider topic rename (gps → global_position) |
| robust_9ffffca | deployment-wiring exclusion (E2 step 3) |
| B-Ver-01 | ROS 1 md5 mismatch, excerpt-based (definitions quoted in a Q&A thread) |
| B-Res-03 | CONCURRENT exclusive-resource claim (ros2_control#1179) |
| B-Beh-02 | ROS 2 QoS, revision likely unpinned (rosbridge_suite#551) |

Agreement between the two initial seats: eligibility 5/5, class 7/7, provenance 12/12, loudness 4/5, resolution 4/5 (Cohen's κ undefined where every pair agrees on one category; 0.0 on the two domains with one disagreement each).

## Findings and protocol changes made before the freeze

**Round 1, packet 00 (ROBUST, 3 cases, 12 min, all three judged ineligible).** Archived in `pilot/round1/`.

1. `robust_9ffffca` → `deployment_wiring` (E2 step 3). Correct; the scope rule works as intended.
2. `robust_248cb38` → `internal` (E2 step 2). Wrong, and the rule was at fault: S1 read "nothing at its boundary changed" as "no declared interface changed", although a wrong value (quaternion component order) crosses the mavros→FCU boundary. Excluding such cases would remove exactly the interface failures that contracts cannot express. **Change:** E2 step 2 now defines `internal` as "would occur with any correct peer"; a wrong value, frame, unit, component order, name, or timing crossing the boundary is an interface failure wherever the fix lives. New class `representation_convention` (no matching rule; an honest miss category). S1 correctly followed the primary source over the ROBUST description (component order, not frame; PR #351 / issue #352).
3. `robust_263650d` → `internal` because the `mavcmd` script and the `global_position` plugin share one catkin package. **Change:** a unit is a separately deployable component (node or process, library, firmware image, package); two nodes interacting only through ROS interfaces are separate units even in one package; UPGRADE requires separately released or built units, and includes a consumer written against an earlier provider revision (`consumer_built_against` justified from the reference). S1 also found no observed failure in the source (latent fallback path). **Change:** E4 accepts a code-level statement of the mismatch; new outcome class `undocumented`, in the funnel but in no failure denominator.

Re-run of `robust_248cb38` and `robust_263650d` under the refined prompt: packet `S1_pilot_02.json` (round 2).

**Round 1, packet 01 (ROS corpus, 3 cases, 16 min).**

4. `B-Beh-02` (rosbridge#551) → eligible, PAIR, `qos_reliability`, silent, resolution `recommended` (fix merged, reporter never confirmed). Correct. But the provider is the reporter's own node with no repository: S2 cannot describe it, so the case would be `unassessable`. **Change:** a unit with no public code may be described from verbatim source statements of interface attributes (the reporter's "Best Effort" publisher), as an excerpt-based unit in the excerpt stratum; a unit with neither code nor such a statement stays `unassessable`.
5. `B-Res-03` (ros2_control#1179) → `internal`, because the minimal fix changes only the service's return code. The source documents two defects: the co-activation of two controllers claiming one command interface (rejected by the resource manager, so the switch failed; loud) and the wrong `ok=True`. **Change:** multi-defect sources are judged defect by defect; the case is eligible if any defect is an interface failure, and the internal one is recorded as `other`. Such a case counts for RQ1 in the loud stratum, not for RQ2.
6. `B-Ver-01` (ROS Answers 226746) → eligible, UPGRADE, loud (md5 mismatch at connect), `definition_mismatch` + `element_removed_or_renamed` + `element_retyped`, resolution `observed`, excerpt-based with `artifacts/B-Ver-01.txt`. S1 recomputed both md5sums from the quoted definitions and they match the logged values; it marked this as its own computation. Revisions unpinned (no public repository for either unit).

Round 3 re-runs `B-Res-03` and `B-Beh-02` under the multi-defect and excerpt rules (`S1_pilot_03.json`).

**Round 2 (`robust_248cb38`, `robust_263650d`, 13 min).** Both eligible under the refined rules: 248cb38 → PAIR, failure, silent, `representation_convention` (S1 again followed the maintainer's diagnosis over the ROBUST title; the FCU firmware unit has no identifiable repository); 263650d → UPGRADE with `consumer_built_against` = provider tag 0.12.0, outcome `undocumented`, resolution `recommended` (fix commit only, never shown running). S1 recorded the PAIR-at-one-revision alternative in notes, as the protocol asks.

**Round 3 (`B-Beh-02`, `B-Res-03`, 16 min).** Both eligible. B-Beh-02: PAIR, `qos_reliability`, silent, excerpt-based provider (reporter's statement), resolution `recommended`; S1 also listed a `/tf_static` durability defect that the fixing PR addresses in a different composition. B-Res-03: PAIR client ↔ controller_manager service, `other` ×3, loud, resolution `recommended`; S1 did not model the two controllers' co-activation as the case's composition, because the reporter's problem was the response value. **Change:** "one case is one composition": S1 specifies the composition whose failure the reporter reports as the problem; all documented failed interactions of that composition are conditions (runtime-enforced refusals included, as `loud`); other compositions go to `notes`. Round 5 re-runs both (`S1_pilot_05.json`).

**Round 4 (`B-Ver-01`, 17 min).** Eligible, UPGRADE, loud (md5 at connect), three classes, resolution `observed`, excerpt-based; `consumer_built_against` now a provider label (`md5:20a63a1c…`) with a matching artifact section, plus provider `md5:cb87164d…` and consumer `as-reported-2016-02`. `materialize.py --only B-Ver-01` produced three excerpt tasks (u0008–u0010) and per-task artifact files; the ledger now records which packet each task went to, so re-runs never rewrite a packet an S2 agent is reading.

**S2 packet 01 (3 excerpt tasks, 7 min).** All three described with per-field provenance; md5 recomputed by the tool from the definition texts (20a63a1c… and cb87164d…). Three defects found: (a) the S1 artifact carried an error line and md5 values and bracketed context labels, and S2's `blinding_guess` for u0010 was "yes" on the strength of the error line. **Change:** artifacts hold only definition/configuration/code text and verbatim attribute statements; no logs, hashes, labels. (b) The per-unit element list lets S2 see that a revision lacks a listed field (u0010 has no `raw`). Inherent to computing UPGRADE deltas; recorded as a residual in Section 6 and measured by the blinding-guess rate. (c) S2 invented its own signature formats (joined with `; `); two runs describing two revisions could then differ on formatting alone. **Change:** fixed signature templates in the S2 prompt (a message's signature is its definition id); the assembler collapses whitespace. S2_01 will be re-run under the final prompt before the freeze.

7. `B-Ver-01` spec (round 1): `consumer_built_against` was a description, not a provider revision label, and the artifact file had no section for the provider at the built-against revision, so `materialize.py` could not create that task. **Change:** the prompt now requires a provider revision label (commit, tag, release, or artifact-section label) and, for excerpt-based UPGRADE cases, a provider section at the built-against revision. Round 4 re-runs `B-Ver-01` (`S1_pilot_04.json`).

**S2 packet 00 (7 mavros snapshot tasks in one run, 25 min): discarded.** All seven descriptions were written with per-value provenance, but the run disclosed that "to locate the changed regions quickly" it ran `diff` between snapshots of different tasks, and that the diffs steered which regions it read. Two `blinding_guess` answers were "yes" (u0002 on the Eigen `Map` component order; u0004 on `gps/fix` not being advertised). This is the failure the protocol reviews warned about (a behavioural rule is not an access boundary): a run that holds several revisions of one repository can reconstruct the pairing, and the point of S2 is that it cannot. **Change:** materialisation now builds one isolated workspace per unit@revision (`s2_work/tasks/<task>/` with only `packet.json`, `S2_PROMPT.md`, the snapshot or `artifact.txt`, `definition_hash.py`, `recon/`), and S2 is one run per task confined to that workspace; the multi-task packet format is gone. The seven descriptions are archived in `pilot/s2_round1_mavros/` (old task ids; mapping in `pilot/ledger_round1.json`) and are not used downstream. Provenance discipline itself held: every value cited its own snapshot; what the diff contaminated was attention, not values.

**S2 packet 01 re-run (3 excerpt tasks, final prompt, 5 min).** Signatures now follow the templates; `not_declared` used correctly (u0010: `field:os5000_imu/imu_data.raw` with the complete-body justification); the tool's md5 output matched the quoted values. But the B-Ver-01 artifact (round 4, written before the artifact-content rule) still carried the error line, both md5sums and bracketed labels, and u0010's `blinding_guess` was again "yes" on the strength of the error line. Kept in `pilot/s2_round2_excerpt/` as reference; not used. Round 6 re-runs B-Ver-01 under the final prompt.

**Round 5 (`B-Beh-02`, `B-Res-03`, 19 min).** Both eligible under the one-composition rule.

8. `B-Beh-02` → PAIR, `qos_reliability`, silent, resolution `recommended` (PR #690 adds a launch test of exactly this composition but no run or CI record is in the source). The artifact follows the content rule (code lines with path comments, verbatim attribute statements, no logs or labels). Defect found downstream: the case-level `excerpt_based` flag made *every* unit of the case excerpt-described, including `rosbridge_server`, which has a repository and pinned revisions. **Change:** `excerpt` is per unit (S1 sets it; for older specs a unit without a repository is excerpt-described); `materialize.py` snapshots the units with repositories and quotes only the units without. `rosbridge_server@1a2c386` and `@adfa4d6` are now snapshot tasks; only the reporter's publisher is quoted.
9. `B-Res-03` → PAIR (`ros2 service call` ↔ `controller_manager`), class `other` only, silent: under the one-composition rule the reporter's problem is the wrong `ok=True` return value, and the two-controller resource conflict that V18 filed this case under is a different composition, recorded in `notes`. So the pilot's intended CONCURRENT resource case is, by the primary source, an honest miss for every method; this goes into the correction ledger (V18 class Res → v2 class `other`). Two S1 defects: (a) `broken_rev` was prose ("humble branch as of … (branch head 945d64ed …)") and `git archive` cannot resolve it; (b) the consumer's `resolved_rev` was null while the resolution was `observed`, because the fix was shown working with a different client (`ros2 control`), which is an observation on a different composition. **Change:** `broken_rev`/`resolved_rev` are bare git revisions with the reasoning in `revision_basis`; a unit the resolution does not change keeps its broken revision; `observed` requires both units of the resolved composition identified by revision, otherwise `recommended` with the sibling observation as evidence. `materialize.py` now records the commit each revision resolved to (`resolved_commit`), so branch names given with `pinned: false` are still reproducible from the ledger. Round 6 re-runs `B-Res-03` and `B-Ver-01` (`S1_pilot_06.json`).

**S2, one run per task (u0004–u0013, 10 runs, 1.5–9 min each, ~250k tokens each).** All ten wrote a valid file with a provenance key for every non-null value, and none reported reading outside its workspace. Consistency across runs that never saw each other: the three `mavros_node` snapshots agree on the seven `~cmd` services and disagree exactly where the code differs (`gps/fix` declared at 0.12.0, `not_declared` at 263650d and 4fb6e7e with `global_position/raw/fix` declared instead); the two `mavcmd` snapshots reference `gps/fix` at 4fb6e7e and the new names at 263650d. Blinding guesses: "yes" on 5 of 10 (both `mavcmd`, `mavros_node`@263650d, `rosbridge_server`@1a2c386, `setpoint_attitude`@3a82c90), "cannot_tell" on 4, "no" on 1; for the rename case the element list itself (old and new name asked together) is what gives it away, the residual recorded in Section 6. Two defects: (a) `rosbridge_server`@adfa4d6 (u0013) recorded `reliability: reliable` although the fixed code chooses the profile at run time from the discovered publishers, which would make the resolved composition a false alarm for ECM and DQ. **Change:** a QoS value chosen at run time from peers or external configuration is null, with the rule in `notes`. (b) `not_declared` was used for a consumed element in one run and not in the other. **Change:** `declares`/`not_declared` cover provided elements only. u0012 and u0013 re-run under the final prompt (`pilot/s2_round3/` holds the first versions).

**End-to-end on `robust_263650d` (UPGRADE, `undocumented`).** Assembled from blind descriptions: broken composition ECM `right_reason` (`field_break` on `topic:/mavros/gps/fix`, the implicated element), NT and SV `accept`, DI and DQ `wrong_reason` (two `di_definition_mismatch` findings on services); resolved composition all five `accept`. Steward check of the DI findings against both snapshots: `CommandLong.srv` lost its constants block and `CommandInt.srv` gained a `broadcast` field between 0.12.0 and 4fb6e7e, so the findings are real definition changes on other elements and rule-instance matching classified them correctly. They also show the cost of an inferred `consumer_built_against`: `mavcmd` was built with the same `mavros` commit and merely kept an old topic name, and modelling that as "built against 0.12.0" exposes every provider change since 0.12.0 to every checker. **Change:** `consumer_built_against.basis` (`documented` / `inferred`) recorded by S1 and reported as a stratum. `robust_248cb38` is `unassessable` (the FCU unit has no repository), as S1 predicted.

**Workspace frozen at dispatch.** The u0013 re-run reported that `packet.json` and `S2_PROMPT.md` changed under it (mtime 16:33 → 16:38): a `materialize.py` re-run, made to refresh the prompt of not-yet-run tasks, rewrote a workspace whose run was already in flight, because "dispatched" was inferred from the presence of the description file. The run had read the prompt at its start and its output conforms to both versions, so nothing is invalidated, but the boundary was porous. **Change:** the steward marks a task `DISPATCHED` (timestamped marker in the workspace) before handing it to a run, and a dispatched workspace is never rewritten; the test suite covers it.

**End-to-end on `B-Beh-02` (PAIR, `qos_reliability`, silent, excerpt provider + snapshot consumer).** After the u0012 third run (static default `reliable`/`volatile` with the rclpy citation) and the u0013 re-run (run-time-selected QoS → null): broken composition ECM `right_reason` and DQ `right_reason` on `topic:/my_topic` (best_effort offered, reliable requested), NT/DI/SV `accept`; resolved composition all five `accept`. This is the expected shape for a QoS failure: the platform proxy detects it as well as the checker, so the case carries no checker-only credit, and the fixed composition is not a false alarm once run-time selection is recorded as undeterminable rather than as its default.

**Round 6 (`B-Ver-01`, `B-Res-03`, 20 min).** B-Ver-01: S1 settled which side was stale by recomputing the md5sums (the five-field body hashes to the publisher's value, the six-field body to the client's), so the Pi publisher was current and `/control_panel` the stale build; UPGRADE with `consumer_built_against` = the six-field definition, resolution `observed` (the reporter rebuilt and it worked); artifact bodies now hold definition text only. Defect: the consumer's sections came out empty, because the "no hashes" rule made S1 drop the whole connection header, which is the only evidence of what the consumer references. **Change:** a runtime record is quoted with its hash fields removed; its `message_definition` goes to the built-against provider section, the remaining fields (topic, type, caller id) stay with the consumer. Also, an empty artifact section is now `evidence_inadequate` rather than an empty file. Round 7 re-runs B-Ver-01. B-Res-03: PAIR, two `other` conditions, `loud_documented` at activation, resolution `recommended` (the STRICT workaround; no fix PR references the issue), both units pinned to the branch heads on the reproduction date with `revision_basis`; snapshots `ros2_control@945d64ed` and `ros2cli@61f98ce6` exported. Renamed units left three undispatched tasks orphaned; `materialize.py` now withdraws such tasks (entry kept, workspace removed) and allocates ids from a monotone counter.

**End-to-end on `B-Res-03` (PAIR, `other` ×2, loud at activation).** Broken composition: all five methods `not_supported` (no rule matches an `other` condition; no method emitted a finding); resolved composition (same revisions, the STRICT request parameter as the recommended workaround): all five `accept`. The case is an honest miss for every method and produces no false alarm, which is the behaviour the class table specifies. Two request-field edges first came out `unassessable_edge` (`port_missing_producer`). The describer had copied the packet's sides correctly (`ros2service` provides `field:…start_controllers` and `field:…strictness`); the assembler was at fault: it took the case-level roles (provider = `controller_manager`) for every element and ignored the inventory's per-element sides, so a request field that flows client → server was looked for on the server. **Change:** `edge_units` now orients each edge by the element's own sides and records the direction; test and mutation added. After the fix all five edges assemble (`done`) and the case outcome is unchanged.

**Round 7 (`B-Ver-01`, 9 min).** Under the header rule the consumer sections now hold the connection header's interface fields (`callerid`, `tcp_nodelay`, `topic`, `type`) with `md5sum` and `message_definition` removed; the six-field `message_definition` is the provider section at the built-against label, sub-definitions included, and the five-field msg listing the provider at the running label. `consumer_built_against.basis` = `documented`. S1 again verified the direction by recomputing both md5sums and cross-checked the migrated Stack Exchange text against a Wayback snapshot. The provider unit is named `os5000_imu` again (round 6 had `os5000_imu_publisher`), so the two provider tasks already described under the old name (u0017, u0018) are marked `superseded` in the ledger and re-run under the new name (u0021, u0022), with the two consumer tasks (u0019, u0020); the three undispatched orphans are withdrawn. Lesson for the freeze: unit names are part of the task key, so an S1 re-run that renames a unit costs a re-description; after the freeze S1 runs once per case and the question does not arise.

**Adjudication A1, packet 00 (5 items: B-Beh-02, B-Res-03, B-Ver-01, robust_248cb38, and the E2-exclusion sample robust_9ffffca).** Adjudicators run in isolated workspaces built by `adjudicate.py prompt` (packet, S1 prompt, specs, artifacts; for A2 also the assembled composition and the cited task workspaces), so the "do not open scores" rule is structural. withdrawn_google (Gemini) returned in 6 min with `agree` on every decision of every item; its records carry verbatim quotes with URLs from the primary sources (issue bodies, the mavros PR, the ROS Answers thread, the turtlebot commit), so the verdicts are evidenced. First adj1 run failed on environment: the `workspace-write` sandbox has no network by default (DNS failures on every source) and the record directory was a symlink outside the sandbox. **Change:** records are written inside the workspace and copied out by `adjudicate.py collect` (never overwriting); the adj1 runner passes `-c sandbox_workspace_write.network_access=true`. Re-run below.

**All six cases scored (pre-adjudication).** `robust_248cb38` unassessable (FCU unit has no repository); `robust_263650d` (UPGRADE, undocumented) ECM right_reason, DI/DQ wrong_reason, NT/SV accept, fix accepted by all; `robust_9ffffca` ineligible (deployment wiring), adjudication sample; `B-Ver-01` (UPGRADE, ROS 1 md5, loud at connect) ECM right_reason (`field_break` on `msg:os5000_imu/imu_data`, the consumer's header names the type and the definition changed), DI and DQ right_reason on the message and its five retyped fields, NT/SV accept, fix accepted by all; `B-Res-03` (`other`) all not_supported, fix accepted; `B-Beh-02` (QoS) ECM and DQ right_reason, others accept, fix accepted. So on the pilot the checker is never alone on a loud case, alone once on a silent undocumented one, and nothing false-alarms on a fix. A2 items are now merged per distinct evidence (one item per method, rule, and triggering provenance, listing the elements covered): 18 raw findings became 5 items.

**Adjudication summary and freeze.** The pipeline's last stages ran on the pilot as they will run on the corpora: `adjudicate.py items` (A2 merged per distinct evidence), isolated adjudicator workspaces, `collect`, `fold` (splits recorded and sent to the third seat by `third`), `scoring.py --adjudicated`. The one split arose on `robust_248cb38`, whose specification predates the rules on resolution status; the third seat applied the current rule (`observed` needs both units identified by revision) and the case's resolution became `recommended`, with no effect on any score because the FCU unit has no repository. adj1's A2 excerpts are its own readings of the files; withdrawn_google's are in part copies of the item's provenance strings, so the A prompt now requires the adjudicator's own quoted lines and treats an unopened location as `unverifiable`. Final pilot scores (pre- and post-adjudication identical): `B-Ver-01` ECM/DI/DQ right_reason; `B-Beh-02` ECM/DQ right_reason; `robust_263650d` ECM right_reason (undocumented outcome, no failure denominator); `B-Res-03` all not_supported; `robust_248cb38` unassessable; no false alarm on any resolved composition. Protocol, prompts, scripts, runners, and ledgers frozen after this summary (`FREEZE.json`); pilot cases stay quarantined (`pilot/PILOT_CASES.json`).
